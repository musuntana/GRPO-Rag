# RagOS Competitive Survey

Research date: **2026-10-04**. Scope: 30+ projects across open-source RAG platforms, workflow/agent orchestration, multi-tenant white-label chat builders, LLM gateways, and RAG frameworks.

## 0. How to read this document

- This is **market intelligence, not architecture**. `docs/architecture.md` remains the single source of truth for design decisions.
- If this document and `docs/architecture.md` disagree, `docs/architecture.md` wins — **and this document must be updated in the same change** (per `AGENTS.md` working rules 7 and 10).
- Primary sources only: official documentation, license files, source repositories, pricing pages. Every factual claim carries a URL.
- Claims labeled `INFERENCE` are our reasoning, not verified fact.
- Three items could not be verified and must be checked before they influence a purchase or adoption decision. See §8.

Each pattern in §6 is the upstream justification for a rule in `docs/architecture.md`. The `Refs` column points at the architecture section that rule landed in, so the two documents can be diffed together.

## 1. Executive findings

**1. Two of the most popular projects are legally off-limits for our business model.**

Dify's license states: *"Multi-tenant service: Unless explicitly authorized by Dify in writing, you may not use the Dify source code to operate a multi-tenant environment. Tenant Definition: Within the context of Dify, one tenant corresponds to one workspace."* ([LICENSE](https://github.com/langgenius/dify/blob/main/LICENSE)). Maintainers confirm this reading in [issue #4685](https://github.com/langgenius/dify/issues/4685). FastGPT's license allows commercial backend use but prohibits offering the product as a SaaS ([README](https://github.com/labring/FastGPT)).

The precedent we can cite runs the other way: n8n's Sustainable Use License explicitly permits using the automation layer as a backend for your own application with *your* company credentials, and permits commercial consulting and support around it ([Sustainable Use License](https://docs.n8n.io/privacy-and-security/sustainable-use-license)). That is our exact business shape — host the automation and retrieval layer, expose AI capability to customers under our own credentials, and sell the platform as a service.

**2. This category is losing projects, so do not treat any single OSS project as a foundation.**

| Project | Status |
|---|---|
| [Flowise](https://github.com/FlowiseAI/Flowise) (~55k stars) | Code frozen 2026-07-29, repository archived, official EOL 2026-08-31 ([sunset notice](https://flowiseai.com/sunset)). Acquired by Workday in Aug 2025. |
| [Verba](https://github.com/weaviate/Verba) (~7.7k stars) | Archived 2026-06-08; *"no longer actively maintained"* per Weaviate ([blog](https://weaviate.io/blog/verba-open-source-rag-app)). Last release 2025-07-14. |
| [Quivr](https://github.com/The-Vibe-Company/quivr) (~39k stars) | Officially discontinued 2026-04-10; no main-branch commits since 2025-06-19; self-hosted app removed from the repo ([announcement](https://www.thevibecompany.co/resources/articles/quivr-to-the-vibe-company)). |
| Dify / FastGPT / MaxKB / Onyx | Real multi-tenancy is gated to a commercial edition or an X-Pack add-on in every case. |

INFERENCE: vendor-sponsored reference applications are not durable foundations, and a permissive license is not the same as a maintained codebase.

**3. Dify does not use LangGraph.** Its workflow engine was extracted into a Dify-owned library, `langgenius/graphon`, currently pinned at `graphon==0.5.1`, with no `langgraph` dependency in `api/pyproject.toml` ([pyproject.toml](https://github.com/langgenius/dify/blob/main/api/pyproject.toml), [workflow_entry.py](https://github.com/langgenius/dify/blob/5aae5c15/api/core/workflow/workflow_entry.py)). The project reports accumulating breaking changes since the split ([issue #35376](https://github.com/langgenius/dify/issues/35376)).

This is a datapoint in favor of our LangGraph choice, with a caveat: LangGraph's own self-hosted multi-tenancy story is its weakest area (no default authentication; isolation requires hand-written metadata filters plus store namespace rewriting — [auth docs](https://docs.langchain.com/langsmith/auth), [store auth](https://docs.langchain.com/langsmith/store-auth)). See ADR-0005.

**4. Five of our design rules are occupied white space, not "nice to have."**

| Our rule | State of the market |
|---|---|
| Collections organized by embedding profile, tenants isolated by payload filter (guardrail 4) | Dify uses **one collection per knowledge base** ([qdrant_vector.py](https://github.com/langgenius/dify/blob/main/api/core/rag/datasource/vdb/qdrant/qdrant_vector.py)); RAGFlow uses **one index per tenant** ([es_conn_base.py](https://github.com/infiniflow/ragflow/blob/1b295222/common/doc_store/es_conn_base.py)). Only Onyx shares our topology ([document_index_utils.py](https://github.com/onyx-dot-app/onyx/blob/c6a758db/backend/onyx/document_index/document_index_utils.py)). Nobody uses Qdrant native sharding ([Qdrant multitenancy](https://qdrant.tech/documentation/manage-data/multitenancy/)). |
| CRAG relevance gate with re-retrieve on ambiguous and refusal on irrelevant | **Zero implementations** across ten projects. Dify exposes only a static similarity score; RAGFlow defaults to `similarity_threshold=0.2` ([doc.py](https://github.com/infiniflow/ragflow/blob/74b44e1a/api/apps/sdk/doc.py)). |
| Three-tier memory with fact extraction and decay | Only RAGFlow ships a real memory module, and it landed in 0.23.0 (Dec 2025) ([release notes](https://ragflow.io/docs/release_notes)). **Dify and FastGPT have no long-term fact memory at all.** |
| Contextual chunking (Anthropic-style) | Only Onyx ships it in OSS ([indexing_pipeline.py](https://github.com/onyx-dot-app/onyx/blob/f83e4d93/backend/onyx/indexing/indexing_pipeline.py)); Dify's request is a stale open issue ([#8776](https://github.com/langgenius/dify/issues/8776)). Anthropic measured retrieval-failure reduction from 35% to 67% ([contextual retrieval](https://www.anthropic.com/engineering/contextual-retrieval)). |
| Memory architecturally separate from enterprise KB (guardrail 8) | Only RAGFlow separates them in storage ([memory docs](https://ragflow.io/docs/use_memory)). Everyone else merges or omits. |

**5. Sandboxing is the weakest security surface in this market — which makes it the strongest thing we can sell.**

- **Flowise** shipped three RCE advisories against its NodeVM "sandbox": a CVSS 9.9 authenticated RCE from missing route-level authorization ([GHSA-9rvc-vf7m-pgm2](https://github.com/FlowiseAI/Flowise/security/advisories/GHSA-9rvc-vf7m-pgm2)); caller-supplied `nodeVMOptions` overriding security defaults ([GHSA-3769-jgqc-cxm7](https://github.com/FlowiseAI/Flowise/security/advisories/GHSA-3769-jgqc-cxm7)); and an SSRF filter bypass because the deny-list applied only to axios/node-fetch while bare `http`/`https`/`net` were allowlisted ([GHSA-xhmj-rg95-44hv](https://github.com/FlowiseAI/Flowise/security/advisories/GHSA-xhmj-rg95-44hv)). It also silently downgraded from E2B to NodeVM when `E2B_APIKEY` was unset.
- **MaxKB** shipped **CVE-2025-53927** (RCE in the tool module) and **CVE-2025-53928** (RCE during MCP calls) ([v2.0.0 notes](https://github.com/1Panel-dev/MaxKB/releases/tag/v2.0.0)).
- **AnythingLLM**'s SQL agent has **read-write database access by design**; the only documented mitigation is to use a read-only DB user ([User Guide](https://doccompiler.ai/api/v1/jobs/shared/job_1776340060878_245ad982/download/Mintplex-Labs__anything-llm__UserGuide.pdf)). Its Agent Flows API Call block is unauthenticated outbound HTTP.
- **Dify**'s `CodeExecutor.execute_code` hardcodes `"enable_network": True` regardless of the sandbox's own setting ([code_executor.py](https://github.com/langgenius/dify/blob/40df83de/api/core/helper/code_executor/code_executor.py)).

No project has a single tenant-scoped, egress-policy-enforced execution path that HTTP nodes, Script nodes, MCP tools, and agent flows all traverse, with per-call audit. See ADR-0003.

## 4. Table stakes

Missing one item is a procurement blocker; missing three is a lost deal. Every item below appears across essentially all credible products in at least two of the four categories.

**Identity and RBAC**

1. SAML SSO plus OIDC on the enterprise tier (Botpress is the only product in our set where we could not evidence it).
2. SCIM 2.0 user and group provisioning. Only Open WebUI publishes this capability; everyone else handles lifecycle through OIDC group sync or manual invites.
3. A group primitive synced from the IdP, usable directly as an ACL principal, so one grant covers a 500-person group.
4. Custom roles plus **resource-level** ACLs with a small fixed permission ladder. Knowledge bases, documents, retriever profiles, workflows, prompts, tools, and MCP servers are all ACL-bearing resources, not just workspaces.
5. Separation of builder seats from end-user volume. End users of a customer's bot must never consume the builder's seat budget.
6. Scoped administrative delegation and scoped API keys.

**Branding**

7. Widget de-branding — remove the vendor logo.
8. Tenant-owned custom domain.
9. Theme, CSS, JS, and typography control including RTL.
10. **Multiple brands inside one tenant.** Voiceflow is the only product that names this use case explicitly: tag sources `plan: enterprise` versus `plan: self-serve`, *"useful when you have multiple brands, product lines, locales, or subscription tiers"*, and filter at query time. This is exactly our optional `brand_id` field — treat it as a first-class retrieval filter, not a folder.

**Operations**

11. Audit log of who did what, when, from which IP, including sign-ins and configuration changes, **readable through an API**. Chatwoot is the most explicit; most others ship tracing, which is not an audit log.
12. Per-run trace viewer with retrieved sources, tool calls, token usage, and cost. Retrieval explain is the single most-wanted screen in an RAG product and the least consistently built.
13. Retention, residency, export, and DSAR handling.
14. Compliance artifacts and an SLA — SOC 2 Type II or ISO 27001, willingness to answer custom security questionnaires.

**Commercial**

15. Volume tiers with overage packs, threshold alerts, and a stated overage policy.
16. Storage metered as separate typed quotas. Botpress is the only vendor that itemizes it: table rows, **vector storage** (100MB/1GB/5GB), and file storage as separate lines ([pricing](https://botpress.com/pricing)). For a RAG SaaS, vector plus file storage is the second-largest cost line after tokens, and nobody else prices it.

## 5. White space

Nine gaps where no open-source project does well. Each maps to a rule already in `docs/architecture.md` — which is the point: our differentiation is real, and it needs to keep being defended rather than assumed.

1. **Tenant isolation enforced centrally and failing closed.** Every project except Onyx resolves tenant context ad hoc per call site, and the result is a systematic bug class — RAGFlow's confirmed bug had five endpoints using the dataset owner's tenant and two using the requester's, producing silently stale chunks. Nothing in the market has a single mandatory resolution point plus defense-in-depth RLS plus a test harness asserting cross-tenant non-leakage. **Onyx is the only project that fails closed** (`raise ValueError("Tenant ID is required for multi-tenant")`). Refs: §5.1.1, §5.3, ADR-0005.
2. **A real long-term memory layer with lifecycle management.** Only RAGFlow has one, and it shipped in Dec 2025. Nobody has fact decay, confidence scoring, memory-versus-KB separation enforced in storage *and* retrieval, memory recall as a parallel channel, and writeback as a first-class pipeline stage. Dify and FastGPT have no fact memory at all. Refs: §7.3.
3. **CRAG-style relevance gating with re-retrieval on ambiguity and refusal on irrelevance.** No relevance grader, no `ambiguous` branch, no refuse path across the ten projects surveyed. Refs: §8.4.
4. **Contextual chunking as a configurable, prompt-cached default.** Only Onyx ships it. Given the measured 35%→49%→67% failure reduction and near-zero marginal cost under prompt caching, this is the highest-leverage unimplemented feature in the survey. Refs: §7.4.
5. **Tenant-scoped sandboxed execution as a platform primitive.** See finding 5 above. Refs: §11, ADR-0003.
6. **Retrieval quality as a measured, versioned, regression-gated pipeline.** Dify has a retrieval test page and FastGPT has app-level evaluation, but no project ships per-KB eval datasets with faithfulness and context-precision metrics, retriever-profile versioning, and a gate that blocks a regression. There is also no profile-driven fusion: RRF appears nowhere and everyone ships ad-hoc weighted fusion with hardcoded defaults. Refs: §8.3, §13.3.
7. **Verified attribution, and retrieval tuned on the customer's own data.** The gap above is measurement; this is what the measurement is *for*. Two things are absent across all ten projects. First, **no platform verifies that a citation it produced actually supports the claim** — RAGFlow, the strongest document-ingestion implementation in the set, extracts deep page and table structure and then emits a citation that no downstream check ever tests, and no surveyed platform publishes a citation-accuracy figure at all. Second, **no platform trains a reranker**: all ten either rent a cross-encoder or ship none, so none can adapt a ranker to a tenant's confusable pages (Q1 beside Q2, summary beside detail, superseded policy beside current). Owning the eval corpus and the training corpus is the same asset, and it is the one lead the survey shows nobody contesting. Refs: §8.6, §13.3, §13.3.2, ADR-0006, ADR-0007.
8. **Vector-store topology done correctly at scale.** The market is split and both halves fail at scale — Dify creates one HNSW index per knowledge base, RAGFlow creates one index per tenant so one noisy tenant degrades everyone. Onyx and FastGPT get the topology right, but nobody offers shard-key promotion, tiered isolation, or embedding-model migration without a reindex. **No RAG platform uses Qdrant's documented `is_tenant` sharding.** Refs: §6.3.2, §6.3.4.
9. **Workflow-engine portability.** Dify's engine is a proprietary extraction with breaking changes; RAGFlow is rewriting its backend mid-1.0-RC. Nobody lets you export a versioned portable definition that compiles to a runtime you own. Quivr and Verba show the terminal risk: the code survives, the product does not. Refs: §9.1.

## 7. Metering and packaging

Three patterns exist in the market:

1. **Per conversation or session** — Botpress defines it tightly ("any exchange with at least two messages from the end user"; three minutes of voice counts as one conversation) and explicitly rejects seat pricing: *"Priced for the work it does, not the seats it fills"* ([pricing](https://botpress.com/pricing)). Typebot uses the same idea, cleaner: *"1 chat equals a row in your Results table."*
2. **Seats for the human layer, usage stacked on top** — Chatwoot is the purest: per agent per month plus AI credits, so the bill scales with headcount and usage simultaneously. CopilotKit charges per builder seat and meters MAU, threads, and storage separately.
3. **Bundled opaque "AI spend"** — Botpress includes $25 (Plus) / $150 (Team) defined as *"$0.10 per conversation, covered by us"*; Chatwoot bundles credits with $20 per 1,000 overage and publishes no per-interaction unit cost.

Outcome-based pricing is rejected on the record by the leader: *"Resolution pricing creates disputes over what 'resolved' means and, perversely, raises your bill when your bot gets smarter. With conversation pricing, a better bot means lower headcount cost — not a higher invoice"* ([Botpress pricing FAQ](https://botpress.com/pricing)).

**Recommendation.** Use Botpress's three-part shape, changing one thing:

- **Platform fee per tenant**, priced on builder seats and tenant count, never on end-user volume — deflected volume is exactly what you do not want to penalize.
- **Included run/conversation volume plus metered AI spend**, billing the measured token cost of generation, embeddings, contextual enrichment, and memory writeback, passed through at a disclosed multiplier, with hard per-tenant caps.
- **On cap, auto-degrade to a cheaper `model_profile` — do not auto-recharge.** Botpress automatically purchases more at 95% of the cap. For an enterprise tenant, silently charging more is the fastest way to lose billing trust; degrading is defensible and visible.
- **A storage tier naming vector, file, and checkpoint volume explicitly.** Botpress is the only vendor that itemizes vector storage, and in a RAG product it is the second-largest cost line after tokens.

Add the one thing nobody in this set does: **per-workflow and per-node cost budgets with a cost-breakdown export.** The reason is structural rather than cosmetic. Contextual chunk enrichment and memory writeback create large costs that are *not* proportional to conversation count, so a flat "conversations plus a fixed unit price" meter will systematically over- or under-charge tenants running different pipelines. Expose `{retrieval_tokens, generation_tokens, enrichment_tokens, memory_tokens, tool_ms, sandbox_ms}` per run and let tenants set budgets on them.

Do not meter purely by token — tenants cannot predict their bill. Do not meter by resolved outcome — see the Botpress argument above.

## 8. Risks

1. **Two of our guardrails have been productized by a competitor.** LangSmith now sells an **LLM Gateway** with cost controls, rate limiting, model fallbacks, and PII/secret redaction, and separately sells **Sandboxes** ([pricing](https://www.langchain.com/pricing)). Guardrail 6 (no Script execution in the API or worker main process) and guardrail 9 (no direct provider calls) therefore have less exclusivity than when `docs/architecture.md` v1 was written. INFERENCE: differentiation must rest on retrieval quality and tenant isolation, not on architectural tidiness. This is the main reason §13.3 and §5 of this survey matter more than §11.
2. **Per-tenant capacity isolation is a vacuum.** n8n has a single global `N8N_CONCURRENCY_PRODUCTION_LIMIT` with no per-project or per-workflow limit, so one runaway workflow in one project degrades every other project. Activepieces sells per-project execution priority as a paid feature. `tenant_ctx` does not provide this — it needs a real fair-share scheduler. Refs: §11.0.
3. **The observability tradeoff should be written down, not left implicit.** LangGraph's durability axis is checkpoint-based, not replay-based event sourcing. That buys tolerance for non-deterministic LLM code but means there is no complete event-history audit log. `docs/architecture.md` §9.2 now records this as an accepted tradeoff.
4. **A category-wide pattern in untrusted code execution.** Four separate projects shipped RCEs in their tool or MCP execution path (Flowise ×3, MaxKB ×2). Budget for adversarial review of `packages/sandbox` and `packages/toolhub` accordingly.

### Unverified before you rely on them

1. **Helicone `ai-gateway`'s license.** Repository metadata and GitHub's detector report GPL-3.0; the README and the npm package say Apache. Read the `LICENSE` file directly. This is blocking for any proprietary SaaS dependency.
2. **LiteLLM's guardrail OSS-versus-enterprise boundary.** Guardrails are documented as configurable per key, team, and model via pre-call hooks, but the documentation we read does not state which guardrail classes ship in the MIT tree. Verify before planning coverage on it. We do not depend on this either way — see ADR-0004.
3. **Morphik Core's SPDX identifier.** Described as open source; the specific license text was not confirmed. Low priority — we recommend against the dependency regardless.

All performance and cost-reduction figures attributed to Bifrost, Helicone, and RouteLLM are vendor self-reported. Bifrost's own competitive comparison table is published by Bifrost and should not be treated as neutral.
